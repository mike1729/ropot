# Qwen3.8 development experiment 05

Run date and analysis date: 2026-10-29. Both chains completed.

Direct JSON edits with thinking disabled fixed the submission bottleneck:
29 of 32 replies became executed candidates, with no truncation. None was
automatically accepted. One candidate met the measured program constraints but
nominated the wrong menu case; repair unnecessarily discarded its useful edit.

## Configuration and evidence

- Model: local Qwen3.8-27B MLX 8-bit; thinking disabled in every request.
- Sampling: temperature 1.0, top-p 0.95, top-k 20; no reasoning-effort parameter.
- Batch settings: 8 completions, prefill batch 2, prefill chunk 256.
- Eight tasks, two independent chains, at most one repair per proposal.
- Initial output limit: 768 tokens; repair output limit: 2048 tokens.
- Planned budget: 32 replies, 45,056 output tokens; all 32 replies dispatched.
- Each reply specifies target_case, old and new. Exact replacements apply to
  the original program; old must occur exactly once. Multiline edits are allowed.
- Repairs retain the previous edit and measured feedback, or local application
  diagnostics. Chains have independent seeds and search state.
- Historical Qwen3.6 B1 benigns remain exploratory cross-checkpoint inputs.
- No private confirmation results inform this analysis.

- Valid JSON and schema: 31/32 (96.9%). One initial reply was empty.
- Applicable exact replacements: 29/32 (90.6%); two had zero matches.
- Executed candidates: 29; all reconstructed programs compiled.
- Candidates passing all statement examples: 10/29 (34.5%).
- Automatically accepted attacks: 0/29 candidates, 0/8 tasks.
- Truncation: 0/32 (0%).
- Useful accepted attacks per minute: 0 over 7.39 minutes.
- Semantic rejection rate: undefined, because no candidates passed automatically.

The final report records two duplicate submitted programs across chains; the
edit-level duplicate guard rejected none within a chain. Distinct replacement
spans can produce identical normalized code. These are separate notions of
duplication and should not be conflated.

## Near-success: task 329, chain 1 initial proposal

The edit changed `k1 = (n_count - 1) // 2` to
`k1 = (n_count + 1) // 2` but nominated menu case 8.
All three examples passed; only menu case 3 failed (expected 0, observed 1).
Token churn was 2/26, with unchanged conditional and comparison counts.
The sole recorded violation was named_case: case 8 remained correct.

The repair feedback explicitly showed the target passing and case 3 failing.
Repair selected case 3 but changed the program to `k3 = e_count // 2` instead
of preserving the previous edit. The new candidate failed three menu cases,
above the allowance of two, and its newly nominated case 3 remained correct.

Retaining the initial edit and nominating case 3 would satisfy the recorded
mechanical and behavioral conditions. This is a counterfactual analyst finding,
not an accepted submission or formal semantic review. The edit is a plausible
localized off-by-one fault.

## Resources and interpretation

The first-chain repair resource sample recorded MLX peak memory about 32.4 GiB;
the second-chain repair recorded about 31.6 GiB. Their final samples showed
normal memory pressure and swap below the experiment baseline.

Compared with run 04, the experiment reached execution reliably and cheaply.
Repairs showed no consistent quality improvement: they often exchanged one
violation for another, failed to preserve a nearly valid candidate, or invented
replacement text absent from the original. The comparison changes both response
format and thinking mode, so their separate effects cannot be isolated.

## Follow-up issues identified, not implemented in this report

1. When named_case is the only violation, feedback should explicitly recommend
   preserving the edit and selecting a measured failing menu case.
2. The current duplicate guard ignores target_case and rejects the same replacement
   with a new target. This would block legitimate retargeting. Reuse existing
   execution results to reassess the new target while charging the proposal slot.
   No actual retarget-only submission occurred in this run.
3. Consider a small separately budgeted reasoning phase followed by mandatory
   edit submission, to retain proposal quality without allowing indefinite analysis.
4. A case-selection relaxation must be recorded as an experimental rule change;
   counterfactual retargeting must not silently inflate the present run's yield.
